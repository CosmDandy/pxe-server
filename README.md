# pxe-server

Переносимый PXE-сервер: разворачивает загрузку по сети, чтобы ставить систему
на серверы без установочной флешки.

Целевой сценарий — серверы, подключённые к ноутбуку **напрямую по Ethernet**
(или через отдельный свитч). Изолированный сегмент вместо общей сети:
DHCP-broadcast не выходит за его пределы и не мешает чужим машинам.

Проверено на живом железе: Dell PowerEdge T20 (UEFI, `snponly.efi`) и
T30 (UEFI, `ipxe.efi`) — включение по Wake-on-LAN, меню, автоустановка
Ubuntu, установка Proxmox через netboot.xyz.

## Как это устроено

Продукт разделён на два слоя.

| Слой | Что это | Где |
|------|---------|-----|
| **Роль** | идемпотентная настройка PXE-сервера | `ansible/` |
| **Стенд** | Linux-VM на macOS, где роль обкатывается | `lima/` |

Роль не привязана к гипервизору — её можно применить к Lima-VM, к железному
серверу или к Raspberry Pi. Стенд заменяем.

### Что делает роль

Поднимает `dnsmasq`, совмещающий три функции:

- **DHCP** — выдаёт клиенту адрес и сообщает, где взять загрузчик
- **TFTP** — отдаёт загрузчик и ядро
- статику на PXE-интерфейсе

Клиент сообщает свою архитектуру в DHCP-опции 93 (`client-arch`), и dnsmasq
отдаёт соответствующий iPXE-загрузчик. Поддерживаемые архитектуры описаны
списком в `ansible/roles/pxe_server/defaults/main.yml`:

| client-arch | Клиент | Загрузчик |
|---|---|---|
| 0 | x86 legacy BIOS | `undionly.kpxe` |
| 7, 9 | x86_64 UEFI | `ipxe.efi` |
| 11 | arm64 UEFI | `ipxe-arm64.efi` |

Добавить архитектуру — дописать запись в этот список; логика роли не меняется.

## Что откуда грузится

| Пункт меню | Источник | Автоустановка |
|------------|----------|---------------|
| Ubuntu Server | свои ядро, initrd и ISO по HTTP | да, autoinstall |
| Proxmox VE, memtest, утилиты | netboot.xyz по chainload | нет |

Разделение намеренное: своё — там, где нужна автоустановка с конкретными
ответами, чужое — там, где задача сводится к каталогу образов.

### Выход в интернет для клиентов

PXE-сегмент изолирован, но netboot.xyz качает образы сам, с целевой машины,
поэтому сервер выступает для сегмента маршрутизатором: включает форвардинг,
маскарадит трафик на внешнем интерфейсе и объявляет себя шлюзом и DNS
(опции 3 и 6). Внешний интерфейс определяется по маршруту по умолчанию,
либо задаётся через `pxe_wan_interface`.

Отключается через `pxe_nat_enabled: false` — тогда опции 3 и 6 объявляются
пустыми, и клиенты не уводят на PXE-сегмент маршрут по умолчанию.

Установщику это тоже полезно: он тянет обновления, а поставленная система
сразу оказывается в сети.

### Почему Proxmox не свой

Установщику Proxmox нужен доступ к образу целиком: ядро с initrd весят 56 МБ
при ISO в 1.7 ГБ. Штатный способ — `proxmox-auto-install-assistant
prepare-iso --pxe`, который делит подготовленный образ на файлы для сетевой
загрузки. Утилита поставляется только под amd64 и на arm64-стенде под
`qemu-user` не читает ISO, падая с «not able to be installed automatically».

Обойти через `sanboot` не выходит: iPXE отдаёт образ как CD средствами BIOS,
но ядро Linux эту эмуляцию не видит — установщик уходит в бесконечное
`searching for block device containing the ISO`.

Код Proxmox-ветки сохранён и включается `pxe_proxmox_enabled: true` — на
amd64-хосте он рабочий.

## Требования (macOS-стенд)

- `lima` — из nixpkgs
- `socket_vmnet` — в nixpkgs отсутствует, ставится из исходников как root:

  ```bash
  git clone https://github.com/lima-vm/socket_vmnet.git
  cd socket_vmnet && sudo make PREFIX=/opt/socket_vmnet install.bin
  limactl sudoers > /tmp/lima-sudoers
  sudo visudo -c -f /tmp/lima-sudoers
  sudo install -m 0644 /tmp/lima-sudoers /etc/sudoers.d/lima
  ```

- USB-Ethernet адаптер; сеть `pxe` в `~/.lima/_config/networks.yaml`:

  ```yaml
  pxe:
    mode: bridged
    interface: en6   # имя из networksetup -listallhardwareports
  ```

`socket_vmnet` требует QEMU-бэкенда — в `lima/pxe.yaml` задан `vmType: qemu`
(Apple Virtualization framework его не поддерживает).

## Запуск

```bash
limactl start lima/pxe.yaml          # поднять стенд
cd ansible && ansible-playbook site.yml
```

По умолчанию роль настраивает всё, но **оставляет dnsmasq остановленным**.
Включение — осознанное действие:

```bash
ansible-playbook site.yml -e pxe_service_enabled=true
```

## Безопасность

`dnsmasq` раздаёт DHCP. Если PXE-интерфейс окажется воткнут не в целевой
сервер, а в общий свитч, он начнёт отвечать чужим машинам и ломать им сеть.

Поэтому:

- сервис по умолчанию выключен (`pxe_service_enabled: false`)
- `bind-interfaces` — dnsmasq слушает строго PXE-интерфейс
- включать только когда кабель идёт **напрямую в целевой сервер**

Признак изолированного сегмента: интерфейс получил `169.254.x.x` (APIPA) —
значит чужого DHCP в сегменте нет.

## Грабли

**Хост-машина берёт адрес из PXE-пула.** Мост делает USB-Ethernet хоста
обычным клиентом сегмента, и macOS охотно берёт там адрес, уводя на него
маршруты. Лечится с двух сторон:

- на сервере — MAC хоста в `pxe_dhcp_ignore_macs` (см. `inventory.yml`)
- на хосте — отключить IPv4 на адаптере:

  ```bash
  sudo networksetup -setv4off "USB 10/100/1000 LAN"
  ```

Для PXE это ничего не ломает: сервер живёт в VM и работает через мост
напрямую, участие хоста в сегменте не нужно.

**dnsmasq объявляет себя шлюзом.** По умолчанию он рассылает DHCP-опции 3
(router) и 6 (DNS) со своим адресом, даже если не просили. Клиенты уводят на
PXE-сегмент маршрут по умолчанию и теряют доступ в основную сеть. Выхода
наружу здесь нет, поэтому обе опции объявлены пустыми — это отключает их
рассылку.

**Одинаковые имена сетевых сервисов в macOS.** Два USB-адаптера видны как
`USB 10/100/1000 LAN` и `USB 10/100/1000 LAN 2` — легко отключить не тот.
Сверяться по имени устройства:

```bash
networksetup -listnetworkserviceorder
```

**DNS за NAT не резолвит: `bind-interfaces` против `bind-dynamic`.**
`bind-interfaces` привязывает сокеты dnsmasq намертво к PXE-интерфейсу —
слушать он может, а переслать DNS-запрос вышестоящему серверу через внешний
интерфейс уже нет. Клиенты получают резолвер, который молчит. `bind-dynamic`
даёт ту же изоляцию без этого эффекта.

**MTU за многослойным NAT.** Путь клиента наружу (socket_vmnet → NAT VM →
NAT Lima) пропускает пакеты только до ~1400 байт; полноразмерные 1500
молча теряются, и загрузки зависают без ошибки. Клиентам раздаётся
`dhcp-option=26,1400`.

**Зависание iPXE на конкретной карте.** На части сетевых карт штатный
`ipxe.efi` виснет на длинных передачах (симптом: мелкие файлы проходят,
большие — нет). Лечится `snponly.efi` — он работает через сетевой стек
UEFI-прошивки вместо собственных драйверов. Назначается конкретной машине
полем `loader` в `pxe_dhcp_reservations`.

**Переткнул USB-адаптер — мост умер.** socket_vmnet не переживает
передёргивание адаптера: линк есть, а трафик через мост не ходит, тихо.
Лечится перезапуском VM (`limactl stop pxe && limactl start pxe`).
Проверка моста: `arping` из VM на адрес хоста.

**Wake-on-LAN и способ выключения.** WoL работает только после корректного
ACPI-выключения (пункт Power off в меню, `systemctl poweroff`). После
жёсткого выключения кнопкой карта не переходит в дежурный режим и magic
packet не слышит. Старые прошивки тоже ломают WoL: на T30 он заработал
только после обновления BIOS с 1.0.0.

**Петля chainload.** iPXE после старта делает собственный DHCP-запрос. Если
не отличать его от прошивки, он получает в ответ свой же загрузчик и грузит
себя по кругу. Различается по DHCP-опции 175, которую ставит только iPXE:
прошивке отдаётся загрузчик, iPXE — скрипт меню.

**PXE-интерфейс уводит маршрут по умолчанию.** DHCP на PXE-сегменте приносит
свой default route с низкой метрикой и перебивает выход в интернет, из-за чего
`apt` перестаёт работать. Поэтому роль настраивает сеть до установки пакетов, а
на PXE-интерфейсе задаёт статику без шлюза.
